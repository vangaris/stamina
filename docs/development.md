# Development

## Local

Node 22+ and pnpm 10 (`corepack enable`). No Docker or Postgres install is needed: local and test databases are an embedded real Postgres.

```bash
pnpm install
pnpm --filter @stamina/api db:dev          # Postgres on :54329 in apps/api/.pgdata, migrated; Ctrl-C stops it
cp apps/api/.env.example apps/api/.env
pnpm --filter @stamina/api dev             # API on :8787
pnpm --filter @stamina/web dev             # web on :5173 (VITE_API_URL defaults to :8787)
```

One terminal instead of three: `pnpm dev` starts the database, waits until it is migrated, then the API and the web app, prefixes each line with its process name, and stops all three on Ctrl-C. It creates `apps/api/.env` from `.env.example` when missing (the `NEON_AUTH_BASE_URL` in it is a placeholder, so real sign-in needs a real Neon Auth URL; `VITE_SERVICES_MODE=dev pnpm --filter @stamina/web dev` runs the web app on the in-memory fake API instead).

| Task                                   | Command                                    |
| -------------------------------------- | ------------------------------------------ |
| lint (incl. module boundaries)         | `pnpm lint`                                |
| typecheck, build                       | `pnpm typecheck`, `pnpm build`             |
| seam 1 (API) and seam 2 (app-core)     | `pnpm test`                                |
| seam 3 (Playwright + axe, phone width) | `pnpm --filter @stamina/web e2e`           |
| UI kit only (dev page, no DB or API)   | `pnpm --filter @stamina/web e2e:ui`        |
| only what a branch changed             | `pnpm affected`                            |
| new migration                          | edit `src/db/schema.ts`, `pnpm --filter @stamina/api db:generate` |

- Seam 1 uses `TEST_DATABASE_URL` when set (CI points it at a Postgres service container), otherwise starts an embedded Postgres.
- `pnpm --filter @stamina/web e2e` starts its own Postgres (:54330, data in `apps/api/.pgdata-e2e`, so it never clashes with a `db:dev` that is already running), API (:8788) and built web (:4173). Set `PLAYWRIGHT_BASE_URL` to run it against a deployed preview instead.
- The onboarding and sign-in Playwright specs need the local stack (they skip against `PLAYWRIGHT_BASE_URL`): onboarding seeds a fresh invite per test by running the `invites:create` script (below) through `e2e/support/create-invites.ts`, and signs in with the fake Neon Auth server (code `424242`). With `VITE_SERVICES_MODE=dev` (no API) the in-memory fake API knows two invite codes, `FAKE_INVITE.validCode` (redeemable once per page load) and `FAKE_INVITE.usedCode` (never valid), exported from `@stamina/app-core`.
- **Onboarding (web).** Flow: `/start` (invite code, checked by `CheckInvite`, remembered in `localStorage` through the `InviteStorage` service) → `/sign-in` → `/onboarding`, which asks `GetProfile` where the person stands (profile saved → Today; no invite remembered → `/start`; otherwise the four screens). Under-18 and non-EU/EEA people are stopped on the device by the domain's `checkEligibility` with nothing sent; the final `SaveProfile` redeems the invite on the server, which applies the same rule again. Code: `apps/web/src/features/onboarding`, `packages/app-core` (requests, fake API, storage), `@stamina/ui-select` (country picker).
- Migrations are forward-only: never edit an applied file, add a new one.
- **Auth and row-level security (API).** Authenticated routes need `Authorization: Bearer <jwt>` (the short-lived Neon Auth token); `authenticate` verifies it with `jose` against the JWKS of `NEON_AUTH_BASE_URL` and sets the pseudonymous `userId`. User-owned tables are touched **only** through `withUser(db, userId, fn)` (`apps/api/src/db/with-user.ts`): one transaction as the NOLOGIN `stamina_app` role with `app.user_id` set, because Neon owner roles and local superusers bypass RLS. Each user-owned table's migration enables and forces RLS, adds a policy on `app_user_id()` and grants its privileges to `stamina_app`. Tests mint tokens with a local Ed25519 JWKS (`apps/api/test/support/test-auth.ts`), so real verification runs without Neon.
- **Screening encryption key.** The API encrypts Screening answers with `SCREENING_ENCRYPTION_KEY` (base64 of exactly 32 bytes, validated at start-up; a bad value fails fast without printing it). `apps/api/.env.example` carries a fixed development key, so a copied `.env` works; tests use the same fixed key (`apps/api/test/support/test-encryption-key.ts`). Never reuse it anywhere real; each deployed environment has its own key (see [releasing.md](releasing.md)).
- **Consent, Screening and outcomes.** After the profile is saved the web app sends the person through `/consent` (the wellness disclaimer and, as a separate unticked box, consent to process health data; two `POST /consent` calls, each stored as an append-only row with purpose, text version from `CONSENT_TEXT_VERSIONS` in `@stamina/domain`, and language), then `/screening` (ten yes/no questions on one page, a body-area picker when the bone, joint or muscle question is yes, and the starting-level question), then Today or `/referred`. The outcome rules are `evaluateScreening`, `resolveTrainingMode` and `isGoalAvailable` in `@stamina/domain`; the API is authoritative and the in-memory fake API (`VITE_SERVICES_MODE=dev`) calls the same functions. `POST /screening` needs a saved profile and both consents, encrypts the answers (`apps/api/src/crypto`, AES-256-GCM, user id as associated data) into `answers_encrypted` next to the plain outcome columns, and keeps every retake as a new row (the latest wins). A yes to the eating-disorder question turns Nutrition off and switches a body-composition Goal to General fitness in the same transaction. `POST /screening/doctor-ok` records "A doctor has said I can train" for a non-pregnancy referral and makes the training mode Limited. `GET /me/export` and `DELETE /me` are the minimal export and hard delete the Referred screen offers; ticket 20 extends them (CSV, every table, the Neon Auth user, withdrawal). One router guard (`apps/web/src/utils/create-safety-guard.ts`) sends every route that is not in the `UNGATED_ROUTES` allowlist through `GET /safety` first: no profile goes to onboarding, missing consent to `/consent`, no Screening to `/screening`, Referred to `/referred`; an unauthenticated answer goes to `/start` and any other failure to the retry screen on `/screening`, so the guard never lets an unchecked person through. A new route is gated by default.
- **Invite codes.** Onboarding needs an invite code (`INVITE_CODE_LENGTH` characters from `INVITE_CODE_ALPHABET` in `@stamina/domain`). Issue codes on the database the API uses: `DATABASE_URL=<url> pnpm --filter @stamina/api --silent invites:create <count>` (1 to 500; for local dev `.env` supplies `DATABASE_URL`). It prints exactly the new codes, one per line, on stdout and nothing else, so `--silent` matters (pnpm's own banner would break the contract); problems go to stderr with a non-zero exit. A code is redeemed when the person's profile is first saved, not when it is typed, so someone turned away as under 18 or outside the EU/EEA keeps their invite. The script, the public `POST /invites/check` and the rest of the API connect as the migrating user; only redemption runs as `stamina_app`, which can read just the `code` and `redeemed_by` columns of unredeemed (or its own) invites and write the two redemption columns.
- **Exercise library.** About 150 curated exercises, the same for everyone, in `apps/api/src/exercises/data/*.json` (one JSON array of `exerciseSchema` entries per group file, 2-space indented). Names and instructions are imported unchanged from [free-exercise-db](https://github.com/yuhonas/free-exercise-db) (Unlicense, public domain; never its images); every tag (equipment, locations, movement pattern, high-load areas, Session slots, RIR suitability, easier/harder) is Stamina's own. `migrate()` (so `db:dev`, `db:migrate`, the test database, previews and production) validates the files with `loadExerciseLibrary` (a bad file, duplicate id or dangling/self link fails before the database is touched) and `syncExerciseLibrary` makes the `exercise` table equal to them: upsert by id, links in a second pass, rows no longer in the data deleted (stored Sessions reference these ids, so deleting an exercise a Session uses fails; retiring one needs a decision first, for example a `retired` flag). The table is reference data: `stamina_app` has `SELECT` only, and the Worker carries neither the files nor the loader, only the table. `GET /exercises?equipment=&locations=&slots=&excludeAreas=` (signed in; comma lists; an absent parameter does not narrow; an empty `equipment=` means bodyweight only; an unknown value is `400 invalid_request`) answers the library ordered by id through the domain's `selectExercises`: `equipment` is what the person has (an exercise passes only if everything it needs is listed), `locations` and `slots` are any-of, and an exercise that loads **any** excluded area is never returned, whatever else matches, so `highLoadAreas` must be conservative (every area the exercise loads heavily or puts in a demanding or end-range position, stretches included; when unsure, list it). To add or retag an exercise, edit the data file, run `pnpm --filter @stamina/api exercises:review` (regenerates `docs/exercise-library-review.md`, the table Vang reviews: tags, under-tagged areas, images that match the movement) and `pnpm --filter @stamina/api test` (`exercise-data-quality.test.ts` holds the library to its rules: count, every slot and place covered, progressions that keep the movement pattern, consistent tags); the loader (`exercises/node.ts`) checks the files, ids and links on every migration. Changing the table shape is a migration as usual. **Images** are hotlinked from wger (`https://wger.de/media/`), unmodified, at most one per exercise and only when it is clearly the same movement; each carries its author, licence (CC-BY-SA 3.0 or 4.0 only), licence URL and wger page. The licence requires showing the author, the licence with a link and the source wherever the image appears (`@stamina/ui-exercise-image` does), never editing or re-hosting the image, and hotlinking depends on wger staying available (the component shows a fallback when an image does not load).
- **Sport profiles.** The 11 launch sports are `apps/api/src/sports/data/*.json` (one `launchSportDataSchema` file per `LaunchSport`); `migrate()` validates them (`loadLaunchSports`) and seeds each as a draft `sport` row, insert-if-missing, so edits made in the database survive. A sport is visible to everyone only once approved by hand in the Neon table editor; a person's "Other…" sport is a draft shared by everyone who asked for that normalized name and visible only to them (`GET /sports`, RLS policy `sport_visible`, written only through the `request_sport` SQL function). `pnpm --filter @stamina/api sports:draft <sport-id> [--overwrite]` drafts a profile with the AI provider (needs `ANTHROPIC_API_KEY`, Phase B; see [ai.md](ai.md)). Review checklist, SQL to list, approve and reject: [sport-profile-review.md](sport-profile-review.md).
- **Program generation.** `POST /program` creates the signed-in user's Program once (week 1 of Block 1, the reveal week; a repeat returns the stored one) and `GET /program` reads the latest week. Tables `program` (one per user), `block`, `session`, `session_exercise` (migration `0006_program.sql`; owner RLS, forced, app role SELECT + INSERT only; `session_exercise.exercise_id` references the library, so the library sync cannot retire an exercise a stored Session uses). The engine is pure code in `@stamina/domain` (`generateWeek` with `chooseEmphasis`, `planFocuses`, `placeSessions`, `pickExercises`, `prescribe`); every number is in its `config.ts` and `RULES_VERSION` says which rules made a Session. `apps/api/src/program` reads the profile, Screening (only the derived Training mode and excluded-area ids), the person's Sport Profile and the library, calls the engine and stores the result with its inputs hash (SHA-256 of the canonical inputs; never a Screening answer). The week starts the day after generation (UTC; `createApp({ now })` injects the clock). Placement treats a hard Activity as recurring weekly, so a heavy Session near the end of the week also respects the first hard day of the next week. Limited mode has no sport-support slot (nearly every such exercise is a jump, bound or ballistic swing): a Limited Session has warm-up, main strength, accessories-core and cool-down, and the dropped slot's exercise count is added to accessories-core; RIR stays at 3 or more and jump-landing and change-of-direction exercises are excluded everywhere. The week also carries `hardActivityDates` (the person's play days of that week when they play hard and their days do not vary), worked out on every read from the current profile and never stored. Excluded areas never leave a person without a Program while the library can still fill a Recovery Session: a heavy focus (lower or upper) the library cannot fill for the equipment and excluded areas (every slot, Limited caps included) becomes a Recovery Session before placement (`planFocuses`; same dates, same Session count; warm-up, accessories and cool-down only, accessories taking core and mobility exercises first and any other exercise that passes the excluded areas when those run out). With bodyweight and dumbbells, for example, a knee exclusion gives Recovery instead of lower Sessions (and, at 45 or 60 minutes, instead of upper ones too) and a lower-back exclusion gives a week of Recovery Sessions. Refusals are `422` with `not-ready`, `referred`, `no-training-week` or `no-exercises` (the library cannot fill even a Recovery Session). Until a profile answer for equipment exists, Sessions assume bodyweight and dumbbells (`DEFAULT_EQUIPMENT`). The Program is part of `GET /me/export` and goes with the account. The AI then picks the exercises of each Session from the rules' candidates, with a per-Session fallback to the rules picker; the model, caps, call log (`llm_call`, migration `0007_ai_picks.sql`) and prompt rules are in [ai.md](ai.md). Phase A production runs without a provider, so every Session is rules-picked.
- **Sessions: logging, finish, progression.** `GET /sessions/{id}` reads one Session (exercises with names and tagged easier/harder variants, the sets logged so far, the finish record, and per exercise `suggestedWeightKg` and `progression`); `POST /sessions/{id}/sets` and `POST /sessions/{id}/finish` write. Ids are made on the device and every write is replay-safe (`on conflict do nothing`: a replayed set id, a repeated set number or a second finish changes nothing and answers `recorded: false`). Tables `set_log` and `session_log` (migration `0008_session_logs.sql`; owner RLS, forced, app role SELECT + INSERT only, so a log is never rewritten). A Session is completed exactly when it has a `session_log` row; `session.status` stays `planned` because the app role cannot UPDATE it, and `GET /program` and `GET /sessions/{id}` derive `completed`. Load is `sessionLoad(rpe, minutes)` (RPE x minutes, the planned minutes by default). Progression for the next Session is `progressLoad` in `@stamina/domain` (all thresholds in its `config.ts`), applied per performed exercise id to the most recent earlier finished Session that logged it: weight x 0.95 after 2 sets at RPE >= target + 2, else +2.5 kg upper / +5 kg lower when every prescribed set hit the top of the range at or below the target RPE (10 - prescribed RIR), else hold; rounded to 0.5 kg; bodyweight, unweighted and unrated exercises have none. Sets done on a variant do not progress the planned exercise. Logs are in the data export (`setLogs`, `sessionLogs`) and go with the account. Known gap, for a later ticket: the Session and Program routes do not themselves check the current Screening outcome; only the web guard does.
- **Offline logging and sync (app-core).** Ids come from `newId()` (`@stamina/ids`, UUIDv7, made when the person taps Done or Finish). `LogSet` and `FinishSession` are `OfflinePolicy.Queue` requests with a `writeLocal` hook: the `localWriteStep` (after validate, before the queue decision) writes the set or finish to the `SessionLogStore` first, online or offline, so the Session screen shows it with no signal; then the request is sent, or put in the `OfflineQueue` when the device is offline, when earlier requests are still waiting (a finish must not overtake its sets) or when the send cannot reach the server. `GetSessionDetail` and `GetProgram` are `OfflinePolicy.Always` read-through queries: online they fetch and cache in the `PlanCache`, offline they answer from the cache (`AppErrorCode.Offline` when never opened online), and `GetSessionDetail` merges in the local sets and finish the server does not show yet. Production keeps the queue, session log and cache in one Dexie database (`createLocalDatabase`); Test and Dev use memory twins. `createAppSync(...)` replays the queue oldest first through the real handlers, removes an entry once the server will never accept it so it cannot block the queue (its handler resolved, which includes a server `Rejected` or an ignored replay; it failed with a permanent client error, `isRetryableFailure` false: an `ApiError` 4xx except 401, 408 and 429; it no longer parses against its schema; or its type has no handler), stops at any other failure (network, 401, 408, 429, 5xx) keeping that entry and the rest, and shares one run between concurrent calls. The local database holds one person's health data, so `Services.localData` wipes every local table on `SignOut` and after `DeleteAccount`, and `claim(userId)` (called after `api.me()` in `VerifyEmailCode` and `GetSession`) records the owner in the database and wipes it first when another user, or no recorded owner, held it: a sign-out that never ran cannot leak data to the next person. `startSync({ sync, target })` runs it on app open and on the target's `focus` and `online` events (the web app passes `window`). Nothing in this path is logged beyond request type, outcome and duration.
- **Refused writes, retry and sign-out (app-core).** A request definition may carry `undoLocal`, the companion of `writeLocal`: when the server refuses a `Queue` request for good (a permanent client error, `isRetryableFailure` false) the offline queue step calls it before the error reaches the caller, and the sync runner calls it when it drops a queued entry (permanent client error; best effort for an entry that no longer parses; nothing for an unknown type), so a refused set or finish never stays on the device (`removeSet`; `removeFinish(sessionId, finishId)` only removes the finish with that id). `startSync` takes an optional `retryEveryMs` (driven by an injected `IntervalTimer`, the system one by default) and the web app sets it to `SYNC_RETRY_MS` (30 s), so a request queued after a transient failure while online is retried with no focus or online event; `stop()` clears the timer. `SignOut` first runs a sync (the mediator hands handlers its single-flight `context.sync`); if entries are still queued it signs nobody out and rejects `AppErrorCode.UnsyncedData`; `DeleteAccount` still wipes regardless. Moments come from `Clock.wallTime()` (a fixed time in Test mode), never `new Date()` in a handler.
- **Session screen (web).** `apps/web/src/features/session` runs one Session at `/session/:sessionId` (behind the safety guard, no tab bar): Focus mode (one exercise, steppers, RPE chips, `Done · set N`), a full-screen rest timer (`REST_SECONDS` by slot; none after warm-up, cool-down or the Session's last set; the countdown reads the clock, which tests inject), the overview table, swap to the tagged easier or harder variant (kept in `localStorage` per Session until the Session finishes), the finish question and the Load. `useSession` is the one composable; a set is added to the screen before `mediator.send(logSet(...))` answers, and the status line says whether it is saved or only on the phone (`Queued`). The wake lock (`utils/keep-awake.ts`) is held while a Session is open. The week view prefetches every Session's detail so it opens offline and shows Start, Continue or Done. `main.ts` starts the sync once (`utils/start-app-sync.ts`), sharing `useServices()` with the mediator.
- **Activities and Load.** `POST /activities` logs one Activity ("I played": sport, day, minutes, intensity, hot) and `GET /activities/week` reads the week that holds today (UTC, from the API's `now`). The client sends the intensity, never an RPE or a Load: the server stores the RPE (`ACTIVITY_RPE_BY_INTENSITY`: easy 4, moderate 6, hard 8) and the Load (`activityLoad`, RPE x minutes), and the web sheet previews the same number with the same domain function. Table `activity` (migration `0009_activity.sql`; owner RLS, forced, app role SELECT + INSERT only; the id is made on the device, so a replayed id returns the stored Activity with `recorded: false`). A day more than `MAX_ACTIVITY_FUTURE_DAYS` ahead is `Rejected` (`ActivityRejection.DateOutOfRange`); there is no limit back, because an Activity logged offline arrives whenever the device is next online and a refusal would delete it. Weeks are 7-day windows anchored on the first Block's start (else the profile's creation day, else today). Weekly Load is the Session Loads (a finished Session counts on the date it was planned for) plus the Activity Loads (on the day played); `average` is the mean of up to the 4 weeks before this one, from the week holding the user's first entry on (a rest week after that is 0; none before it counts), and is `null` until one such week exists (`summariseWeeklyLoad`). Planned Activities come from the profile's play days with its usual minutes and intensity (`plannedActivities`; none for "It varies", none before the Program starts); an Activity is `planned` when its day is one of them, and a planned day is filled by the first planned Activity logged on it. In app-core `LogActivity` is a `Queue` request like `LogSet`: `writeLocal` puts it in the `ActivityLogStore` (memory in Test/Dev, the Dexie `activities` table in production), so it shows with no signal; `GetWeekLoad` is a read-through query that merges the still-local Activities into the cached week (`mergeLocalActivities`, server copy wins by id). The web sheet (`features/activity`) opens from Today; the week screen lists planned and played Activities per day (a played day outside the shown week gets its own row) with the week Load beside the average.
- **Check-ins and stop flags.** `POST /checkins` sends the daily Check-in (sleep, soreness, energy, each 1 worst to 5 best; the person's calendar day; idempotent by the device-made id) and `GET /checkins/latest` reads the latest. `POST /safety/stop-flags` reports one of seven flags (`StopFlag`: chest pain, fainting, breathlessness, heartbeat, fever, new pain, head knock) from the Check-in's "Anything unusual today?" row or a Session's Stop button; new pain carries the body area and only new pain does. What each flag does is one domain table (`STOP_FLAG_EFFECTS`, read with `stopFlagEffect`): chest pain, fainting, breathlessness and heartbeat pause training until `POST /safety/stop-flags/confirm` ("a doctor has seen me", body `{flags}`: the kinds the person saw; only open pauses of those kinds end, so a flag reported later from another device stays paused, and an empty list is a 400) and show `EMERGENCY_NUMBER`; head knock pauses until confirmed (cleared); a fever makes that day a rest day (`restOn`); new pain adds the area to the excluded ones. `resolveStopState` turns the stored flags into `{pausing, restOn, excludedAreas}`, which `GET /safety` returns. Tables `checkin` and `stop_flag` (migration `0010_checkin_and_stop_flag.sql`; owner RLS, forced, app role SELECT + INSERT; the only update is `stop_flag.confirmed_at`, once, null to a time). A pause refuses a new Program (`ProgramRejection.Paused`, after the Referred check) and generation leaves out `mergeExcludedAreas(screening, stop)`; the server does not refuse sets or finishes because of a pause, since one logged before the flag can arrive later from the offline queue and a refusal would delete it. After a report the person answers `stopFlagEffect(flag).recheck` again through `POST /screening/recheck`: the server merges the latest Screening's answers (decrypted) with those, stores a new Screening and never carries `doctor_ok_at` over. In app-core `ReportStopFlag` and `SubmitCheckin` are `Queue` requests with local stores (`StopFlagStore`, `CheckinStore`; memory in Test/Dev, Dexie in production); `GetSafety` merges local flags with the server's `stop` and the cached one, so a flag reported offline pauses the device at once (`SafetyStatus.Paused`). `ConfirmDoctorSeen` and `RecheckScreening` need the server (`Never`), and confirming first syncs and rejects `UnsyncedData` while a flag is still queued. In the web app the outcome of a flag is worked out on the device the moment it is picked (never waits for the network); `/paused` is the only screen a paused person reaches (its confirm button reads "A doctor has seen me", or "has cleared me" when head knock is the only pause), and when a flag's re-ask was dismissed it is asked there right after the confirmation (the owed flags are kept in `localStorage`; a person who reloads before answering is not asked again, a known gap). On a fever day the safety guard sends the Session route to Today and a rest notice shows, both through `isTrainingBlocked`; the Session screen has the Stop button. A Program the person already has is rewritten by new pain as Session revisions (see Adaptation suggestions), not by a suggestion. No stop flag or Check-in value is ever sent to the AI provider (test: `stop-flag.test.ts`).
- **Adaptation suggestions.** The rules in `@stamina/domain` (`proposeAdaptations`, `applyAdaptation`, `reviseAvoidingAreas`; thresholds in `config.ts`) raise a suggestion from an unplanned hard Activity inside the next heavy Session's recovery window (move a day, else swap to recovery, else one set fewer), a poor Check-in (lighter version, else recovery), soreness (swap the exercises that load the Session's targeted areas, else lighten), an early Deload (Load above 1.3 x the person's average two weeks running, 3 poor Check-ins in 5 days, or 2 finished Sessions at target + 2) and missed Sessions (1 is skipped; 2 in a week repeat the week; 14 days without a finished Session restart the Block with one more rep in reserve). Nothing changes until accepted, and no rule ever adds sets, lowers reps in reserve or moves a Session earlier. `GET /adaptations` evaluates the rules (so time-based triggers and a declined Deload asked again after 3 days appear) and lists the pending suggestions that still apply; `POST /adaptations/{id}/accept` (body `{basis}`: the Session revisions the person saw) and `/decline` decide one, both replay-safe (`recorded: false`). Accepting writes new Session rows with `revision + 1` and `supersedes_id` (a repeated week or restarted Block writes a new Block), so history is never edited; a basis that is no longer the current, unfinished, unstarted revision is `Rejected` as `Stale` with the latest week. A Session with logged sets is never revised. Tables `adaptation` and `adaptation_decision` (migration `0011_adaptation.sql`; owner RLS, forced, app role SELECT + INSERT only; status is derived from the decision row). A reported new pain is not a suggestion: `reportStopFlag` rewrites the current week's unfinished Sessions without the area as new revisions. Reasons are EN/EL templates (`adaptation.reason.<rule>`) filled from whole-number params, never AI text. Code: `apps/api/src/adaptations`, `packages/app-core` (`getAdaptations`, `acceptAdaptation`, `declineAdaptation`), `apps/web/src/features/adaptation`, `@stamina/ui-suggestion-card`.

## Module boundaries

Tags live in each package's `package.json` (`nx.tags`); the rules are in `eslint.config.mjs` and fail `pnpm lint`.

| Tag               | May depend on                                           |
| ----------------- | ------------------------------------------------------- |
| `type:util`       | `type:util`                                             |
| `type:ui`         | `type:ui`, `type:util`                                  |
| `type:domain`     | `type:domain`, `type:util`                              |
| `type:contracts`  | `type:contracts`, `type:domain`, `type:util`                         |
| `type:app-core`   | `type:app-core`, `type:domain`, `type:contracts`, `type:util` |
| `type:app`        | anything                                                |
| `scope:shared`    | `scope:shared` (no Vue, no React)                       |
| `scope:vue`       | `scope:vue`, `scope:shared`                             |
| `scope:react`     | `scope:react`, `scope:shared`                           |
| `scope:server`    | `scope:server`, `scope:shared`                          |

A package gets one `type:` and one `scope:` tag. UI components go in `packages/ui/<name>`, shared utilities in `packages/util/<name>`.

## CI and previews

Workflows are in `.github/workflows/`.

- **`ci.yml`**: `nx affected` lint, typecheck, test, build; the UI kit Playwright job (`e2e:ui`, contrast, tap size, focus, reduced motion, sheet focus trap); Gitleaks (pinned binary, full history); OSV-Scanner on `pnpm-lock.yaml`.
- **`prompt-eval.yml`**: runs the AI evaluation set when a prompt, its schema or the set changes and reports the validator pass rate in the job summary ([ai.md](ai.md)).
- **`pr-title.yml`**: the PR title must be a Conventional Commit (the squash commit message is the title), e.g. `feat: 02 Release, infrastructure and ops pipeline`.
- **`preview.yml`**: per PR, a Neon branch (migrated) + that branch's own Neon Auth (its origin trusted, its `base_url` read) + a Cloudflare Worker `stamina-api-pr-<N>` (`scripts/workers-deploy.mjs preview`) with that branch's `DATABASE_URL` (secret), the preview `SCREENING_ENCRYPTION_KEY` (secret, from `SCREENING_ENCRYPTION_KEY_PREVIEW`) and `NEON_AUTH_BASE_URL` (var) + a Cloudflare Pages alias `pr-<N>` whose `/auth/*` proxy points at that branch's Neon Auth, then `e2e` against it. Closing the PR deletes the Worker and the Neon branch (the branch also expires after 14 days). PRs that only touch docs, tickets or templates skip it.
- **`release.yml`**: release-please keeps a release PR open; merging it tags, migrates production, deploys the API, then the web, then smoke-checks. See [releasing.md](releasing.md).
- **Dependabot** (`.github/dependabot.yml`): weekly grouped npm and GitHub Actions updates. Dependabot PRs get no Actions secrets, so `preview.yml` skips them; CI still runs.

Free-minutes levers: concurrency cancels superseded runs, `nx affected` skips untouched projects, pnpm is cached, doc-only PRs skip the preview.

### One-time setup (needs accounts, not in the repo)

Run `./scripts/setup-services.sh`. It signs `gh` in, creates the private repo, creates the Neon project (Frankfurt, plus a data-free `dev` branch) and the Cloudflare Pages project, sets every secret and variable below, and opens the first PR. You paste in two tokens; it creates everything else. Safe to re-run. Values are kept in the gitignored `.env`.

What it sets:

| Where                         | Name                                   | Value                                                                   |
| ----------------------------- | -------------------------------------- | ----------------------------------------------------------------------- |
| Actions secret                | `NEON_API_KEY`                         | Neon API key                                                            |

## Code standards

The default for every implementation; `/code-review` checks the diff against it. Design first: read `skill://stamina-architecture` (project skill in `.claude/skills/`, built on `skill://codebase-design`), then write down the modules, their interfaces and where tests cross before coding.

### Design

- **Deep modules**: a small interface with a lot of behaviour behind it. The interface is everything a caller must know (types, invariants, ordering, errors), not just the signature.
- **Deletion test**: if deleting a module makes its complexity vanish, it was a pass-through; inline it. If the complexity reappears in every caller, it earns its keep.
- **Seams**: put one where behaviour must vary (real vs fake adapter, e.g. `createServices(env)`), not for hypothetical reuse. One adapter is a hypothetical seam; two is a real one.
- **Testable by shape**: accept dependencies instead of creating them, return results instead of mutating, keep the surface small.

### Folder shape

Every feature, UI component and shared utility (a package, or a folder under `apps/*/src/features/<feature>`) uses the same shape. Create only what is used.

```
packages/ui/stepper/
  src/
    index.ts                 the only public interface: re-exports components, composables, utils, `export type`s
    types.ts                 props, options, events, results (`types/` when it grows)
    config.ts                constants, defaults, tunables
    enums/
      stepper-format.ts      one string enum per file, named after it (kebab-case)
    components/
      Stepper.vue            wiring only: props, emits, template
      Stepper.test.ts
    composables/
      useSpinbutton.ts       Vue state and lifecycle that is not template wiring
      useSpinbutton.test.ts
    utils/
      clamp-to-step.ts       pure functions, one concept per file
      clamp-to-step.test.ts
```

- **Logic is not in the `.vue` file.** An SFC's `<script setup>` calls composables and utils; any exported function or composable is its own file with a test beside it. Pure logic goes in `utils/`, anything touching Vue reactivity or lifecycle in `composables/` (`useXxx`).
- **Types are exported.** Declare props, options, events and results in `types.ts`, import them in the component (`defineProps<StepperProps>()`), and re-export from `index.ts` with `export type { ... }`. Never declare an exported type inline in a component, handler or util.
- **No magic strings: enums.** A closed set of values that code branches on or passes around is a string `enum` in `enums/<kebab-name>.ts` (one per file), re-exported from `index.ts` as a value (`export { ButtonVariant } from './enums/button-variant.ts'`) and used by name everywhere: `status === HealthStatus.Ok`, `kind: HealthStateKind.Degraded`, `case Key.ArrowUp`. Enum values are the existing wire/DOM strings, so JSON, markup and i18n keys do not change. Config maps use computed keys (`{ [ButtonVariant.Primary]: '...' }` typed `Record<ButtonVariant, string>`), zod uses `z.enum(MyEnum)`, iteration uses `Object.values(MyEnum)`. In Vue templates import the enum in `<script setup>` and bind it (`:variant="ButtonVariant.Danger"`); a static `variant="danger"` fails `vue-tsc`, which is the enforcement: comparing an enum to a string literal is a compile error. Not enums: CSS class strings (`config.ts` class maps), static native attributes in templates (`role="tablist"`), DOM event names, i18n message keys, `typeof` checks. Shared keyboard keys and ARIA roles live in `@stamina/a11y` (`Key`, `AriaRole`, `AriaLive`).
- **Constants live in `config.ts`**: defaults, limits, durations, class maps, option lists. No magic values in components or utils.
- **One concept per file**, named after what it exports (`clamp-to-step.ts` exports `clampToStep`; `Stepper.vue` is `Stepper`). No catch-all `helpers.ts` or `utils.ts`.
- **`index.ts` is the seam**: other packages and features import only from it. No deep imports into another module's folders, no cross-feature imports except through `index.ts`.
- **App features** follow the client layering in `AGENTS.md`: `features/<feature>/components` holds the container and presentational components, `composables/` the one composable the container calls, `types.ts` and `config.ts` as above. Shared code moves to a package once a second feature needs it.

### Tests

- Tests sit next to the file they test and cross its interface, not its internals (see `AGENTS.md` "Test seams": domain rules are tested through the API seam, not as isolated units; UI and utility modules get their own interface tests).
- A util or composable extracted for testability must have a test that could fail for a plausible bug; extraction is not a reason to test wiring.

### Review checklist

Module interface small and documented? Any pass-through to delete? Logic out of the SFC and in its own tested file? Types in `types.ts` and re-exported? Any string literal that is really a closed set (use an enum)? Constants in `config.ts`? Anything imported past another module's `index.ts`?

Every package under `packages/` follows this shape. Two exceptions are deliberate: `@stamina/ui-test` (its `config.js` must be plain JS because Vitest loads it through Node) and `@stamina/tokens`'s generated `tokens.css`.

In `apps/api`, a module may add a second entry point, `node.ts`, for code that must stay out of the Cloudflare Worker bundle (reading data files, syncing into the database). The Worker imports only `index.ts`; migrations, scripts and tests import `node.ts`. `apps/api/test/worker-bundle.test.ts` fails if that code ends up in the Worker bundle. `apps/api/src/exercises` and `apps/api/src/sports` are the two modules that do this.

## Design tokens and UI components

**Tokens** (`packages/tokens`) are DTCG JSON in two tiers: `primitive.tokens.json` (raw values; the only file a brand theme replaces) and `semantic.*.tokens.json` (named roles that alias primitives: `bg`, `surface`, `text`, `accent`, `load`, `suggest`, `danger`, `focus`, … plus type, spacing, radius, tap size). `pnpm --filter @stamina/tokens generate` compiles them to `src/tokens.css` (committed; the tokens test fails when it is stale): CSS variables for light and dark (the phone's setting, or `data-theme="light|dark"` on any element) and the Tailwind `@theme` mapping. The default Tailwind palette and scales are removed, so only semantic roles generate utilities: `bg-surface text-text border-border`, `text-sm` (14 px), `p-4` (16 px), `rounded-md`, `min-h-tap` (44 px). Placeholder values: system font, type 12/14/16/20/24/32/48 (`xs sm base lg xl 2xl 3xl`), spacing 4/8/12/16/24/32 (`1 2 3 4 6 8`, plus `0`), radius 8/16/pill (`md lg pill`).

**Components** are one package per component in `packages/ui/<name>` (`@stamina/ui-<name>`), presentational (props in, events out) and framework-light:

- Style with semantic utilities only. `pnpm lint` rejects Tailwind palette classes (`bg-indigo-700`), arbitrary colours and arbitrary px/rem lengths in `packages/ui/**/*.vue`.
- Every user-visible string is a prop or slot (accessible names included); packages never import i18n.
- Interactive elements: native elements first, a visible focus outline (the `focus-ring` utility from the tokens, or `focus-ring-inset` where the edge is clipped), a hit area of at least 44 x 44 px (`min-h-tap min-w-tap`; a small visual control sits inside a 44 px `label` or `data-tap-target` wrapper), and correct ARIA roles/states.
- Motion: use `transition-*` classes (their duration is the `base` token). `tokens.css` collapses all CSS transitions and animations under `prefers-reduced-motion`; code that animates in JS must check `matchMedia('(prefers-reduced-motion: reduce)')`.
- Ids come from `useId()` (every component renders twice on the dev page).
- Tests sit next to the component (`src/*.test.ts`, Vitest + jsdom + `@vue/test-utils`) and call `expectNoA11yViolations` from `@stamina/ui-test`. Colour contrast, tap size, focus indicators and reduced motion need real layout, so the dev page is checked in Chromium by `apps/web/e2e/ui-kit.spec.ts`.

**Dev UI page**: `pnpm --filter @stamina/web dev`, then open `/dev/ui`. It renders every component in a light and a dark container. Add a component by dropping `<Name>Demo.vue` into `apps/web/src/dev/demos/`. The route exists only when `import.meta.env.DEV` is true, so production builds carry neither the route nor the page (`e2e/dev-page.spec.ts` checks it).

## Translations

`packages/i18n` holds the messages: `src/locales/en.json` (the source) and `el.json`, nested, ICU syntax (`{count, plural, one {# set} other {# sets}}`). `pnpm test` fails when an English key has no Greek value, when a Greek message is not valid ICU or uses different arguments, or when Greek has a key English lacks. The web app compiles messages with `intl-messageformat` (`apps/web/src/i18n.ts`) and picks the locale from the phone (`navigator.languages`). Style guide for Greek: informal «εσύ», gym terms with the English name on first use, Greek number format.
